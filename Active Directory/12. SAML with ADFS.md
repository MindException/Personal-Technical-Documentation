### 2. Reverse rewrite host in response headers

![](./MD_Images/12_01002.jpg)

* 경로: `IIS 웹서버` -> `Application Request Routing Cache` -> `Server Proxy Settings` -> `Reverse rewrite host in response headers`
* 값: 비활성화  

해당 값은 기본적으로 체크로 활성되어있으며, 웹서버가 응답하는 헤더 값을 host 값과 같게 변환하게 됩니다.     
일반적으로는 문제가 없으나 Redirect 할 때 문제가 발생하게 됩니다. ADFS에서 로그인하여 인증을 받기 위해 ADFS로 Redirect를 해야하지만 이 부분을 IIS가 SP의 Host명으로 수정하게 됩니다.  

예시
* 활성화: https://app.flask.com/adfs/ls/?SAMLRequest=fVPBjtow~~~~
* 비활성화: https://sts.LSHCorp.com/adfs/ls/?SAMLRequest=fVPB~~~~

위와 같이 활성화하게 되면 Redirect를 못 하기 때문에 결국 로그인이 불가능하게 됩니다.  
추가적으로 ADFS는 `X-Forwarded-For 헤더`가 필요합니다. 위와 같이 ARR에는 기본 설정이 되어있음으로 수정하지 않습니다.

## 2. SP metadata 설정

우선 SP 쪽 metadata Setting은 AWS <-> ADFS Reference을 기준으로 정리합니다.  
제일 처음 살펴볼 곳은 SP metadata 설정입니다. metadata를 통하여 제대로 Trust를 맺어야, Request와 Response가 원활하게 진행됩니다.    
우선 통신 규칙에서는 `advanced_settings.json`을 통하여 설정하며 일반적으로 아래 값만 활성화하는 경우가 많습니다.  

```json
    "security": {
        "wantAssertionsSigned": true,
        "wantNameId" : true,
    },
```
* `wantAssertionsSigned`: SAML Response 파일에 서명을 추가하여, SP 쪽에서 해당 XML 파일이 변질되지 않았는지 확인합니다.  
* `wantNameId`: Request와 Response nameID를 지정합니다.

<br>

> nameID를 설명하기 전, 우선 Claim이 무엇인지 생각하여 봅시다.   
claime은 ADFS 즉, IDP 쪽에서 요청한 속성 값을 SP에게 전달하여 줄 때 이 속성 값들을 Claim이라고 부릅니다.  
이 때, 속성 값들 대표하는 개체명이 필요한데 이것을 SAML에서는 nameID라고 부르게 됩니다.  

<br>  

```xml
<!--metadata sample-->

<md:NameIDFormat>urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress</md:NameIDFormat>
<md:AssertionConsumerService Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
                                Location="https://app.flask.com/?acs"
                                index="1" />
```
* 위 값을 json 파일에서 설정하게 되면, metadata는 위와 같이 표기됩니다.  

<br>
<br>

이제 살펴볼 기본적인 metadata 설정 템플릿은 아래와 같습니다.   

```json
{
    "strict": true,
    "debug": true,
    "sp": {
        "entityId": "https://<sp_domain>/metadata/",
        "assertionConsumerService": {
            "url": "https://<sp_domain>/?acs",
            "binding": "urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
        },
        "singleLogoutService": {
            "url": "https://<sp_domain>/?sls",
            "binding": "urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect"
        },
        "NameIDFormat": "urn:oasis:names:tc:SAML:1.1:nameid-format:unspecified",
        "x509cert": "",
        "privateKey": ""
    },
    "idp": {
        "entityId": "https://app.onelogin.com/saml/metadata/<onelogin_connector_id>",
        "singleSignOnService": {
            "url": "https://app.onelogin.com/trust/saml2/http-post/sso/<onelogin_connector_id>",
            "binding": "urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect"
        },
        "singleLogoutService": {
            "url": "https://app.onelogin.com/trust/saml2/http-redirect/slo/<onelogin_connector_id>",
            "binding": "urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect"
        },
        "x509cert": "<onelogin_connector_cert>"
    }
}
```
_예시 sample은 [개인 저장소](https://github.com/MindException/SSO-with-ADFS/blob/main/SAML_Demo_Flask/saml/settings.json)에서 확인 가능합니다._  

여기서 중요하게 볼 점은 idp의 `x509cert`와 `Service binding`입니다.

1. x509cert  
     * 위에서 "wantAssertionsSigned" 설정을 하였기 때문에 SP에서는 전달된 서명을 복호화하여 확인해야 합니다.
     * 따라서 IDP의 공개키가 필요한데, 해당 공개키는 인증서에 있습니다. 따라서 인증서인 base64로 인코딩된 `.cer`파일의 값을 넣습니다.  
     * _실제 운영환경일 경우, ADFS에서 사용 중인 인증서를 받아서 자동화할 수 있도록 개발을 권장합니다._  

2. SP Service Binding  
_이 부분은 SP가 ADFS에게 어떻게 바인딩 해야할지 알려주는 부분입니다._
    * assertionConsumerService: ADFS에서 인증이 끝난 후, browser를 통하여 SAML Response를 전달해야되는 걸 명시합니다.  
    * singleLogoutService: ADFS가 로그아웃 후, 브라우저 페이지가 SP 쪽으로 가는 것을 명시합니다.  

3. IDP Service Binding  
_이 부분은 ADFS가 SP에게 어떻게 바인딩 해야할지 알려주는 부분입니다._
    * singleSignOnService: SP 화면에서 로그인 버튼 클릭 후, ADFS 폼 인증으로 넘어가는 것을 명시합니다.  
    * singleLogoutService: SP 화면에서 로그아웃 버튼 클릭 후, ADFS 쪽으로 넘어가는 것을 명시합니다.  

위와 같이 설정하여 SP의 metadata를 생성합니다.

## 4. 클레임 발급 정책 편집
Claim은 쉽게 생각하여 AD(IDP)로부터 LDAP으로 가져온 개체 속성을 Client에게 Claim으로 보낸다고 생각하면 편합니다.  

### 4-1. LDAP -> Claim 설정

![](./MD_Images/12_04001.jpg)
* 우선 AD로부터 특성을 가져와야 하기 때문에 `LDAP 특성을 클레임으로 보내기` 템플릿을 선택합니다.  

<br>

![](./MD_Images/12_04002.jpg)
1. 우선 위에서 nameID를 email로 설정하였기 때문에 Email을 가져옵니다.  
2. LDAP -> Claim Mapping
    * 우선 LDAP에서 가져올 개체 특성을 선택합니다.  
    * 그 다음 SP에 보낼 클레임 유형을 선택합니다.  
        * 내부 클레임 유형에 대한 스키마가 있을 경우, 위와 같이 수동 등록하여도 됩니다.  
        * 예시: http://schemas.lshcorp.com/2018/05/identity/claims/LoginID

<br>  

만약 LDAP 특성에서 원하는 개체 특성이 없을 경우, 아래 규칙 언어보기를 참고하여 직접 `규칙 템플릿`을 작성합니다.  

![](./MD_Images/12_04004.jpg)
```powershell
@RuleTemplate = "LdapClaims"
@RuleName = "LDAPclaim"
c:[Type == "http://schemas.microsoft.com/ws/2008/06/identity/claims/windowsaccountname", Issuer == "AD AUTHORITY"]
=> issue(store = "Active Directory", types = ("http://schemas.xmlsoap.org/ws/2005/05/iden
tity/claims/emailaddress", "http://schemas.lshcorp.com/2018/05/identity/claims/LoginID", "
http://schemas.lshcorp.com/2018/05/identity/claims/Mail", "http://schemas.lshcorp.com/2018
/05/identity/claims/Mobile", "http://schemas.lshcorp.com/2018/05/identity/claims/Username"), 
query = ";mail,sAMAccountName,mail,telephoneNumber,displayName;{0}", param = c.Value);
```

#### ++추가) AD LDAP 특성 확인  
* AD User 개체 속성은 DC에서 `사용자 및 컴퓨터`에서 고급 기능 활성화 후에 확인 가능합니다.
![](./MD_Images/12_04003.jpg)

```powershell
@RuleTemplate = "LdapClaims"
@RuleName = "LDAPclaim"
c:[Type == "http://schemas.microsoft.com/ws/2008/06/identity/claims/windowsaccountname", Issuer == "AD AUTHORITY"]
=> issue(store = "Active Directory", types = ("http://schemas.xmlsoap.org/ws/2005/05/iden
tity/claims/mobile"), 
query = ";mobile;{0}", param = c.Value);
```

<br>

### 4-2. NameID 설정

![](./MD_Images/12_04005.jpg)
* AD에서 가져온 email Claim을 NameID로 변환하기 위하여 `들어오는 클레임 변환` 템플릿을 선택합니다.  

<br>

![](./MD_Images/12_04006.jpg)
```powershell
c:[Type == "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress"]
 => issue(Type = "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier", Issuer = c.Issuer, OriginalIssuer = c.OriginalIssuer, Value = c.Value, ValueType = c.ValueType, Properties["http://schemas.xmlsoap.org/ws/2005/05/identity/claimproperties/format"] = "urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress");
```
* 들어오는 클레임 유형은 AD 개체 특성을 선택합니다.  
* 보내는 클레임 유형에서는 nameID를 선택한 후, SP metadata에서 요구한 nameID 형식에 맞춰서 설정합니다.  

위와 같이 설정하게 되면, ADFS에 SP Trust 및 Claim 등록 과정이 끝나게 됩니다.

## 5. logout 구현 및 설정

우선 ADFS SSO를 통한 로그인 기능과 다르게 Web에서 Logout 구현은 세션을 정리해야 한다는 목표가 있습니다.  
구현하게 되면 순서 상 아래와 같이 진행하게 됩니다.  

* `로그아웃 버튼` -> ADFS Redirect -> ADFS 세션 정리 -> SP Redirect -> SP 세션 정리  

```javascript
// Get 주소
https://[ADFS URL]/adfs/ls?wa=wsignoutcleanup1.0

// 예시
https://sts.lshcorp.com/adfs/ls?wa=wsignoutcleanup1.0
```
* 위 주소로 Get를 송신하게 되면, Browser에서 가지고 있던 쿠키 값(`MSISAuth`)을 바탕으로 ADFS에서 세션과 쿠키를 정리하게 됩니다.  
* 모든 정리가 끝난 후, ADFS는 Browser에게 SP metadata에 적혀 있는 `SingleLogoutService` 주소 Browser를 Redirect 시키게 됩니다.  
* _ADFS와 SP 쿠키는 별도이기 때문에 SP에서도 따로 정리해줘야 합니다._

<br>

위 과정을 실제로 확인하는 과정은 아래와 같습니다.  
테스트를 진행하기 전, ADFS 내부 폼 인증이 비활성화된 경우 아래 명령어를 통하여 활성화합니다.  

```powershell
# 비활성화
Set-AdfsProperties -EnableIdpInitiatedSignonPage $true

# 활성화 
Set-AdfsProperties -EnableIdpInitiatedSignonPage $false
```

정상 동작 점검 순서  

1. SP 로그인
2. __https://sts.lshcorp.com/adfs/ls/idpinitiatedsignon.aspx__ 직접 로그인하여 세션 확인
3. __https://sts.lshcorp.com/adfs/ls?wa=wsignoutcleanup1.0__  ADFS 세션 및 쿠키 정리
4. SP로 라우팅 확인
    * 여기서 SP metadata에 등록한 SingleLogoutService로 바인딩하게 됩니다.  
5. __https://sts.lshcorp.com/adfs/ls/idpinitiatedsignon.aspx__ 에 다시 접속하여 로그아웃 되어 있는지 확인

## 6. Web Browser SSO 동작 과정

![](./MD_Images/12_00001.jpg)  
위 동작과정은 아래와 같다.

1. https://app.flask.com 으로 접속
2. SSO 로그인 접속
3. ADFS 로그인 화면 접속 및 SAML Request 전달
4. Post로 접속할 계정 ID/Pwd 전송
5. ADFS에서 인증 후, SAML Request 재요청
6. ADFS로부터 받은 SAML Response /acs 로 전달
7. SSO 로그인 성공

> SAML Request/Response는 `content-type: text/html`으로 전부 Get형태로 SAML을 전달합니다.  

<br>

### 3,5 SAML Request

```xml
<samlp:AuthnRequest xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
                    xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
                    ID="ONELOGIN_bcab392e4c44b09587c43957bc1e2b4551d62d5c"
                    Version="2.0"
                    ProviderName="SP test"
                    IssueInstant="2026-06-01T01:49:01Z"
                    Destination="https://sts.LSHCorp.com/adfs/ls/"
                    ProtocolBinding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
                    AssertionConsumerServiceURL="https://app.flask.com/?acs"
                    >
    <saml:Issuer>https://app.flask.com/metadata/</saml:Issuer>
    <samlp:NameIDPolicy Format="urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress"
                        AllowCreate="true"
                        />
    <samlp:RequestedAuthnContext Comparison="exact">
        <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport</saml:AuthnContextClassRef>
    </samlp:RequestedAuthnContext>
</samlp:AuthnRequest>
```

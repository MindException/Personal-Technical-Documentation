* 실제로 모든 layer가 합쳐진 `merged`는 `/var/lib/docker/rootfs/overlayfs/` 경로에 위치하며 위 예시인 c24a820dbba3와 같이 `CONTAINER ID`로 찾을 수 있습니다.  
쉽게 생각하여서 마운트된 디렉토리의 용도는 아래와 같습니다.  
    * `LowerDir`: 이미지를 구성하는 원본 레이어로 `읽기 전용(Read-Only)` 공간
    * `UpperDir`: 컨테이너가 실행될 때 원본 이미지(LowerDir) 맨 위에 얹어지는 '쓰기 가능(Writable)' 레이어
    * `WorkDir`: 임시 공간으로 lowdir에 있는 파일을 upperdir에서 수정해야 할 경우에 WorkDir에서 먼저 작업을 처리한 뒤 UpperDir로 넘기는 용도
    * `MergedDir` : 합쳐진 최종 파일시스템

</br>

lowerdir에서 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots` 경로를 보면 레이어들을 고유한 번호나 ID로만 관리하고 있습니다.  

```bash
# 4번 Layer FileSystem
root@ubuntu24-01:/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/4/fs# ls
bin  dev  etc  home  lib  media  mnt  opt  proc  root  run  sbin  srv  sys  tmp  usr  var

# 17번 Layer FileSystem
root@ubuntu24-01:/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/17/fs# ls
dev  etc
```
여기서 중요한 점은

* 레이어는 중첩되면서 변경된 부분만 수정하여 이미지를 생성하게 됩니다.
    * 예시로 4번과 17번에서 dev에 같은 이름의 파일이 존재한다고 하였을 때, 결국 17번으로 덮어씌워집니다.
* 따라서 서로 다른 컨테이너 이미지여도 기본이 되는 Lowerdir이 겹친다면 중복되게 다운 받지 않고 공용으로 사용하게 됩니다.

이런 식으러 덮어쓰기가 된다면 컨테이너 이미지는 추후에 용량이 매우 증가하게 될 것 입니다.  
>> 그렇다면 어떤 식으로 이미지 크기를 줄여야 하나요?
* 정답은 레이어를 다시 쌓아햐 한다는 것 입니다.

위와 같이 4 ~ 17번 레이어가 기본 컨테이너 이미지라고 했을 때, 5~16번을 삭제하고 4, 17번으로 레이어를 쌓으면 되지 않을까라는 생각할 수 있습니다. 하지만 이는 호환성에 문제가 발생하여 권장되지 않습니다.  

따라서 4~n 번까지의 레이어가 있는 컨테이너 이미지에서 새롭게 다시 패키징하는 것이 옳바른 방법입니다.
